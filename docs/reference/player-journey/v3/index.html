决定一 · 3D 不退位，换镜头 ✔ 已定

SPEC-0003 要求两个 shell 都落地到 3D 世界；多邻国的证据说落地屏该是一条一次只给一步的路。 两者都对，冲突的是「镜头站在哪」而不是「用不用 3D」。

路径本身早就写好了——layout.ts 的 layoutCourse() 一直在做奇偶行反向、左右摆、往前推、每单元升高，那就是一条盘山蛇形路。 它只是被摊平成 4 个一排、然后从 50° 高空俯视，所以读起来像网格不像路。

已经改完并跑通：折叠 4→1、正弦摆动（周期 7，与单元大小互质）、 保留爬升、俯角 50°→74°、雾改按视线长度算、当前关挂「开始」气泡。 三个镜头（路上 / 飞行 / 俯瞰）是同一个场景的三个相机档位。

过程中撞出两个真 bug：真正的杠杆是 COURSE_POLAR 而不是相机位置 （Controls 把俯角两头钉死，MapControls.update() 每帧覆盖高度）； 以及雾在按「世界多大」算而不是「看多远」，于是雾的起点比画面上任何东西都远。

决定二 · 四层内容压成三层，多出来的那层交给「路径分段」

多邻国是三层：课程（英语/Math）→ Section（第5阶段第1部分，彩色）→ 节点（一节课）。 我们是四层：Study（4）→ Course（52）→ Unit（146）→ Lesson（560）。多了一层。

多邻国我们放在哪
课程切换器（顶栏旗帜下拉，D1）Study · 4顶栏下拉 + 3D 群岛作为富视图
Section（彩色分段，C1–C4）Course · 52路径上的彩色段，一段一个色

节点（C1–C4）Lesson · 560路径上的圆节点

先修关系（DAG）怎么办：我们的 52 门课是有向图不是链条—— turing-pact 是一条 9 环长的主干，然后九条支线同时打开 （证据：apps/online/src/world/layout.ts:49-58 的注释）。一条线画不出图。
解法：路径把图拓扑排序成线，3D 地图保留图的真实形状。 路径说「这是一条对的顺序」，地图说「这是知识真实的样子」。两句话都不假。 拓扑排序我们已经有了——apps/online/src/catalog/listing.ts 的 depthsFromPrerequisites。

决定三 · Web 端不是「把手机版拉宽」，是「把手机版放中间，两边补手机放不下的东西」

这是你问的「web 端 16:9 怎么解决」。答案不是响应式拉伸。 一条 600px 宽的路径放进 1440px 的屏幕，拉宽会让节点间距大到看不出是一条路， 居中留白又浪费掉 60% 的屏幕。

多邻国 Web 端的做法（注：这条我没能亲自验证——duolingo.com/learn 需要登录， 我不会去登录你的账号。这是模型调研结论，不是我量出来的）：三栏， 左侧 ~256px 导航、中间 ~600px 路径、右侧 ~368px 挂件（每日任务 / 排行榜缩略 / 升级推广）。

我们的三栏，右栏放的不是广告，是 3D。 多邻国右边填的是排行榜和促销，因为他们没有别的东西可放。 我们有一座会长房子的岛——16:9 多出来的那块地方，正好是移动端装不下 three.js 的地方。 同一个约束，在两个视口上一个是负担、一个是机会。

性能不在这份文档的讨论范围内。模型还没进来，现有的都是占位几何体， 这时候估体积和帧率是在给还不存在的东西做优化。等模型进来了再量真机、再收敛。 这一版只解决三件事：好看、好用、认知负担低。

骨架导航：逐格照搬多邻国，格子里换成我们的东西

多邻国的导航是经受过考验的，没必要重新发明。 做法：槽位数量、位置、层级一比一照搬；每个槽位里放什么，换成我们的。 我们没有的功能先占位——占位不是偷懒，它是把"这块地方留给什么"提前定死， 免得以后硬塞进别处。

3D美术方向：云上的岛，和 OwnMySpace 同一个世界观

这一节是这一版最大的视觉转向，而且它不是新发明的—— 它是把 University 的选课场景接到你已经在另一个项目里建立的视觉语言上。

从「海上的岛」改成「云上的岛」

/Users/yuanfei/PieAI/OwnMySpace 的定位原文是： 「every player owns a floating platform in the sky above an ocean planet」—— 海洋星球上空的漂浮平台。它的 ART-DIRECTION-V2.md 里画了这张图：

🏝️(别人的小庄园) ⛴️🏘️(云港镇，有暖色灯点) ☁️☁️☁️ ← 云海 ═══════════════════════════════ ← 海洋星球弧面 + 大气 rim

University 用同一套。52 门课不是海面上的岛，是云层之上的浮岛； 往下看是一望无际、被大气雾化的森林与湖泊；选课 = 从一座岛飞到另一座岛。

为什么这值得做：这不是换个贴图。两个产品共用一套世界观之后， 它们互相为对方作证——一个人在 OwnMySpace 拥有自己的浮岛，在 University 沿着浮岛学习， 他会认为这是同一个世界，而那正是一个品牌能给的最贵的东西。 而且它顺手解决了一个我一直没解决的问题：现在的海面是一整片死平的青绿色， 没有任何东西能让画面有纵深，因为水面本来就是平的。云层不是。

直接继承 OwnMySpace 已经踩过的坑

它的 ART-DIRECTION-V2.md 是一份用真实截图逐帧诊断出来的文档。 下面这些是它的结论，我们不用再犯一次。

它的诊断我们现在的状态要做什么
「天空是死白的 —— 这是『廉价 3D demo』最强的单一信号。 没有任何商业游戏的天空是纯灰白。」 我们是青绿渐变，比死白好，但天顶没有饱和的蓝，地平线不暖 天顶饱和蓝 → 地平线偏暖，至少 3 级明度梯度
「云不是云。两套风格并存 —— 风格不统一比丑更伤。」 我们一朵云都没有 先用 drei 的 <Clouds/><Cloud/> 评估，一套风格，宁少勿杂
「远景是飞碟 —— 它无法被解释，所以大脑判定为 bug。」 远处的岛在雾里，勉强可解释 远景必须是可解释的：更远的浮岛群 + 云海 + 底下的森林湖泊
「大气透视是纵深的真正来源，不是加更多几何体。 远的东西必须更淡、更偏天空色、对比度更低。」 ✅ 我们已经按「视线长度」调好了雾（不是按世界大小） 再进一步：FogExp2 + 按高度衰减
「AO 单项性价比第一名。Townscaper 的高级感有一大半来自它。 现在所有物体像贴纸，就是因为没有它。」 需要核实 Stage.tsx 的后处理链里有没有 没有就加：N8AO → 色彩分级 → 克制的 Bloom → SMAA → 极轻 Vignette
「★ 前景框架：让近处的一棵树挡住画面一角（占 5–15%）。 这是摄影里最基本的深度技巧，成本为零。」 ❌ 完全没有前景 路上视角天然适合：近处一丛草 / 一块岩石压住画面下角
「同一物体不许原样重复超过 3 次 —— 那十几棵一模一样的松树。」 我们的 PropField 有实例化，需要核实有没有做随机变化 尺寸 / 旋转 / 色调三项随机

网主路径与岔口：网状学习，但一次只露三个

网状学习确实更符合大脑——关联记忆比孤立记忆牢。 但把 52 门课 558 节课 281 个概念之间的关系一次画出来，那不是地图，是毛线球。 这一节给出的折中是：前方永远只有一条路加最多三个岔口；网只在你身后显现。

你说的「岔出去一个名词解释，比如什么叫前端」和「跳到别的课程」——都是第 ② 层。 第 ③ 层是同样的词条在课文内部被提到时的样子，两者共用同一批内容，只是出现的位置不同。

收敛规则：三格窗

路上视角 · 岔口只在窗口内出现

规则一句话：岔口只在当前节点前后各一格的窗口里出现， 每个节点最多 3 个。

所以屏幕上任何时刻岔口数 ≤ 9，而且这是常数上界—— 52 门课变成 200 门、281 个概念变成 2000 个，屏幕上还是 ≤9。 认知负担不随内容增长，这是这条规则唯一存在的理由。

编程上就是四行 
const SPUR_WINDOW = 1;  // 当前节点前后各 1 格
const SPUR_MAX = 3;     // 每节点最多 3 个岔口
const visible = nodes
  .filter(n => Math.abs(n.index - currentIndex) <= SPUR_WINDOW)
  .flatMap(n => n.spurs.slice(0, SPUR_MAX));

没有图算法，没有力导向布局，没有遍历。一个 filter 加一个 flatMap。 这就是你要的「不要为了实现网状把程序弄得特复杂」。

关键设计：网只在身后显现

前方是路，身后是网。没走过的节点，岔口完全不画——前方永远清清爽爽一条路。 走过之后，那些你点开过的岔口亮着留在原地，而且彼此之间连线 （因为同一个概念会被好几节课引用到）。

你往前走得越远，回头看，身后的网越密越亮。 那张网就是「我学到的东西是互相连着的」这件事本身，被画了出来。

这也是 3D 才做得好的地方：平面上画身后的网会糊成一团， 3D 里往回看是有纵深的——近的清楚，远的淡去，网自然分层。 这是 3D 在这个产品里第一次不是装饰，而是唯一能表达这个信息的媒介。

项目切项目：四条独立的路，不是一条 52 门的长路

一个必须避免的误解

问题在这条主干之后：走完《代码之外》，9 门课同时解锁，而且它们只共享一个先修。

解法：先修是硬约束，顺序是软推荐，两者分开

不要改先修关系，要新增一个字段

先修（prerequisiteCourseIds）说的是「不学 X 就看不懂 Y」——那是真的，不能为了排队去撒谎。 《契约与防漂移》确实只需要《代码之外》打底，硬加一个假先修会让内容说谎。

要补的是另一个东西：推荐顺序。9 门都解锁了，我们建议先学哪个。 加一个 spineOrder（或一份显式有序清单），规则只有一条：

spineOrder 必须是先修 DAG 的一个线性扩展。
也就是：如果 A 是 B 的先修，那么 order(A) < order(B)。

这一条可以写成测试，作者排错顺序 CI 直接红。 这样主路径永远是一条线、永远只有一个下一步，而先修图仍然诚实—— 它退到幕后，只负责「你还没资格进这里」的判定。

任务一和「两端合流」的关系：你说对了一大半

你要求两端几乎一模一样、唯一差异是 AI 接入方式。 我去查了仓库和三份 spec，你的目标完全正确，而且已经被写进了 canonical spec； 但其中一条做法会打破它自己的验收条件，而且不需要打破——目标能用别的做法 100% 达成。

你说的核实结果
「唯一区别是 AI：online 接 API key，local 走剪贴板 + AI 宿主」 ✅ 完全正确，而且早就写下来了。SPEC-0001:141 原话： 「model access（一边是 coding host，另一边是 metered online APIs）」。你记得没错。
「local 找课也变成那片岛」 ✅ 正确，而且已经是一份 active / canonical spec。 SPEC-0003: One World, Two Shells（2026-08-21）第一句就是这件事。 它不需要重新决定，它需要被建出来。
「课文、答题、写课仍然是 2D」 ✅ 正确，而且是 portfolio 硬法。Web3D 基线第 7 条：可读文字是 DOM，永远不是几何体。 中文输入法、屏幕阅读器、文本选择、手机键盘在 canvas 里全部会死。
「local 后端也用 SwimmerBackend」 ❌ 这一条会打破三份文档，而且不做它你也能拿到你要的东西。见下。

为什么「local 用 SwimmerBackend」不成立

先说一个你可能没意识到的事实：apps/online 现在根本没有后端。 它是一个纯静态站点，全仓只有 1 处 fetch （apps/online/src/content/library.ts:116），读的是打包进去的静态 JSON。 没有账号、没有支付、没有 API、没有 AI 调用。SwimmerBackend 在这个仓库里一行代码都没有。

所以「让 local 用 online 的后端」这句话里，那个后端还不存在。 真正该做的是：给 online 建 SwimmerBackend（账号、支付、权限、计费 AI）—— SPEC-0001:140 已经为它留好了位置。而 local 不该接它：

  • SPEC-0001:140 — 共享包不得拥有 storage：「一边本地文件 + SQLite，另一边 SwimmerBackend」
  • SPEC-0001:208 — 验收条件 4：UniversityLocal 内没有 uploader，也没有 backend client
  • SPEC-0003 结尾 Non-Negotiable — 「创作端保持离线。共享一个包不是联网。」

打个比方。你想要的是「我在家做的菜和店里一模一样」。 正确做法是共用同一份菜谱、同一套锅、同一个摆盘——那样你在家改进的任何一步，店里立刻也有。 你提的做法是「我家厨房接店里的中央厨房」——一旦断网，你每天赖以学习的那一端就做不了饭了， 而且它对「共用菜谱」这个真正的目标几乎没有帮助：代码复用发生在菜谱层，不在中央厨房层。

能 100% 达成你目标的做法：把「数据从哪来」切成一个口子

那 18 处 fetch 是两端无法共用课文阅读器的唯一原因—— packages/ui 里的「共享」组件写死了 /api/*，所以 online 用不了，只好自己写了第二份 （apps/online/src/lesson/Lesson.tsx）。这就是你说的「两套代码」，它只有这一个根。

做法：定义几个口（Port），组件只认口，两端各给一个实现（Adapter）。

口local 的实现online 的实现
ContentPort 读课文/单元/课程本地 HTTP /api/*静态 JSON（将来 SwimmerBackend）
ProgressPort 读写进度SQLitelocalStorage（将来账号）
GradingPort 判题剪贴板 + AI 宿主指纹当场判 + SwimmerAIKit
EvidencePort 取代码片段本地 git 检出只给坐标不给内容（私有仓库不进交付包）

这样你要的闭环就成立了：口之上的一切——路径、节点弹窗、阅读器、答题、结算、图鉴、复习—— 是一份代码。你每天用 local 时发现的任何问题，改在口之上，online 自动就有了。 口之下只有四个小适配器，各几十行。
而 local 保持离线，这不是妥协，这是保护你每天要用的那一端。

Grok 和 Gemini 独立审计后给了同一句结论。Grok 原话： 「不要让 local 去用 SwimmerBackend——那是在拆掉你每天用的那一端， 而且对『local 发现的问题自动惠及 online』几乎没有帮助。」

3D 场景放哪：已定，两份 spec 都已改到位

packages/world，一个独立的新包，不是 packages/ui。

packages/ui 是 2D 学习表面，保持零 three—— 这样课文阅读器的单测永远不用起一个假的 WebGL 环境， 任何 import 了 Markdown 组件的模块也不会顺手拖上一个渲染器。 apps/local 只有在主动依赖 packages/world 时才装 three 系列， 那是它一次性、公开做的决定。

2026-08-22 裁决。SPEC-0003 第 1 步已从 packages/ui 改为 packages/world； SPEC-0001 已点名说明「共享包」指的是 core + ui 这套平价套件， 不是「任何两端都 import 的包」。这个矛盾不会再被推导出来一次。
