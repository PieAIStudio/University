决策先看三个决定，其余全是它们的推论

这三条决定了下面每一屏。如果你不同意其中任何一条，先停在这里说， 因为改这三条 = 整份文档重写；改下面任何一屏 = 只改那一屏。

决定一 · 3D 不当落地屏，改当「世界选择器 + 常驻舞台 + 奖励面」 ⟵ 待你拍板

这一条和 SPEC-0003 有冲突，我不替你决定。

SPEC-0003: One World, Two Shells（2026-08-21，active / canonical / owner: human） 第 3 步写着「退役 2D 书架」，Non-Negotiables 写着「一个场景，两个覆盖层」。 它要求两个 shell 的落地屏都是 3D 群岛。

而多邻国官方博客给出的改版理由只有一句：学习者 「不确定自己有没有在用『对的』或者『最好的』方式用多邻国」（blog.duolingo.com, 2022）。 他们的解法是取消选择——把网状技能树压成一条线。 我们的 3D 群岛正是网状技能树的 3D 版：52 座岛按先修关系铺开，一打开就是「你自己看着办」。 这正是多邻国花大力气删掉的东西，我们做了个立体的。

我的方案（三选一里的第三个）：按视口分岗，两份文档同时成立。

视口落地屏3D 在哪SPEC-0003 还成立吗
Web ≥1180px三栏 右栏常驻，一直在你眼前 成立。一个共享场景，两个覆盖层，2D 书架照样退役
Web 768–1180双栏不加载降级，同 SPEC-0003 未覆盖的情况
移动端2D 路径 按需 import()：「看看我的世界」+ 结算庆祝 场景仍是同一个，只是不默认挂载

这样 3D 的三个岗位是：① 世界选择器——4 个 study 是 4 片群岛， 「选学哪个真实项目」是有意义的选择，保留； ② 常驻舞台——桌面右栏，你随时看得见自己站在哪； ③ 奖励面——学完一节岛上真的多一间房，这是多邻国用一句「+40 经验」代替掉的东西，我们有实体。 它唯一不再承担的岗位是「从这里找出下一节课」。

本项目自己早就写过同一句话：v2/build-brief.html 第 ⑤ 屏原话—— 「它是先于 3D 存在的，不是 3D 的降级」。那一屏至今没被建出来（#/catalog 是它的一半）。

决定二 · 四层内容压成三层，多出来的那层交给「路径分段」

多邻国是三层：课程（英语/Math）→ Section（第5阶段第1部分，彩色）→ 节点（一节课）。 我们是四层：Study（4）→ Course（52）→ Unit（146）→ Lesson（560）。多了一层。

多邻国我们放在哪
课程切换器（顶栏旗帜下拉，D1）Study · 4顶栏下拉 + 3D 群岛作为富视图
Section（彩色分段，C1–C4）Course · 52路径上的彩色段，一段一个色
（无对应）Unit · 146路径上的分隔线 + 居中标题（多邻国用它分 section，我们用它分 unit）
节点（C1–C4）Lesson · 560路径上的圆节点

先修关系（DAG）怎么办：我们的 52 门课是有向图不是链条—— turing-pact 是一条 9 环长的主干，然后九条支线同时打开 （证据：apps/online/src/world/layout.ts:49-58 的注释）。一条线画不出图。
解法：路径把图拓扑排序成线，3D 地图保留图的真实形状。 路径说「这是一条对的顺序」，地图说「这是知识真实的样子」。两句话都不假。 拓扑排序我们已经有了——apps/online/src/catalog/listing.ts 的 depthsFromPrerequisites。

决定三 · Web 端不是「把手机版拉宽」，是「把手机版放中间，两边补手机放不下的东西」

这是你问的「web 端 16:9 怎么解决」。答案不是响应式拉伸。 一条 600px 宽的路径放进 1440px 的屏幕，拉宽会让节点间距大到看不出是一条路， 居中留白又浪费掉 60% 的屏幕。

多邻国 Web 端的做法（注：这条我没能亲自验证——duolingo.com/learn 需要登录， 我不会去登录你的账号。这是模型调研结论，不是我量出来的）：三栏， 左侧 ~256px 导航、中间 ~600px 路径、右侧 ~368px 挂件（每日任务 / 排行榜缩略 / 升级推广）。

我们的三栏，右栏放的不是广告，是 3D。 多邻国右边填的是排行榜和促销，因为他们没有别的东西可放。 我们有一座会长房子的岛——16:9 多出来的那块地方，正好是移动端装不下 three.js 的地方。 同一个约束，在两个视口上一个是负担、一个是机会。

这也顺带解决了移动端的性能问题：three + @react-three/fiber + drei 在移动端首屏是实打实的几百 KB 和一次 GPU 唤醒。移动端默认不加载 3D， 只在「看看我的世界」和结算庆祝时按需 import()。

任务一和「两端合流」的关系：你说对了一大半

你要求两端几乎一模一样、唯一差异是 AI 接入方式。 我去查了仓库和三份 spec，你的目标完全正确，而且已经被写进了 canonical spec； 但其中一条做法会打破它自己的验收条件，而且不需要打破——目标能用别的做法 100% 达成。

你说的核实结果
「唯一区别是 AI：online 接 API key，local 走剪贴板 + AI 宿主」 ✅ 完全正确，而且早就写下来了。SPEC-0001:141 原话： 「model access（一边是 coding host，另一边是 metered online APIs）」。你记得没错。
「local 找课也变成那片岛」 ✅ 正确，而且已经是一份 active / canonical spec。 SPEC-0003: One World, Two Shells（2026-08-21）第一句就是这件事。 它不需要重新决定，它需要被建出来。

「local 后端也用 SwimmerBackend」 ❌ 这一条会打破三份文档，而且不做它你也能拿到你要的东西。见下。

为什么「local 用 SwimmerBackend」不成立

先说一个你可能没意识到的事实：apps/online 现在根本没有后端。 它是一个纯静态站点，全仓只有 1 处 fetch （apps/online/src/content/library.ts:116），读的是打包进去的静态 JSON。 没有账号、没有支付、没有 API、没有 AI 调用。SwimmerBackend 在这个仓库里一行代码都没有。

所以「让 local 用 online 的后端」这句话里，那个后端还不存在。 真正该做的是：给 online 建 SwimmerBackend（账号、支付、权限、计费 AI）—— SPEC-0001:140 已经为它留好了位置。而 local 不该接它：

  • SPEC-0001:140 — 共享包不得拥有 storage：「一边本地文件 + SQLite，另一边 SwimmerBackend」
  • SPEC-0001:208 — 验收条件 4：UniversityLocal 内没有 uploader，也没有 backend client
  • SPEC-0003 结尾 Non-Negotiable — 「创作端保持离线。共享一个包不是联网。」

打个比方。你想要的是「我在家做的菜和店里一模一样」。 正确做法是共用同一份菜谱、同一套锅、同一个摆盘——那样你在家改进的任何一步，店里立刻也有。 你提的做法是「我家厨房接店里的中央厨房」——一旦断网，你每天赖以学习的那一端就做不了饭了， 而且它对「共用菜谱」这个真正的目标几乎没有帮助：代码复用发生在菜谱层，不在中央厨房层。

能 100% 达成你目标的做法：把「数据从哪来」切成一个口子

那 18 处 fetch 是两端无法共用课文阅读器的唯一原因—— packages/ui 里的「共享」组件写死了 /api/*，所以 online 用不了，只好自己写了第二份 （apps/online/src/lesson/Lesson.tsx）。这就是你说的「两套代码」，它只有这一个根。

做法：定义几个口（Port），组件只认口，两端各给一个实现（Adapter）。

口local 的实现online 的实现
ContentPort 读课文/单元/课程本地 HTTP /api/*静态 JSON（将来 SwimmerBackend）
ProgressPort 读写进度SQLitelocalStorage（将来账号）
GradingPort 判题剪贴板 + AI 宿主指纹当场判 + SwimmerAIKit
EvidencePort 取代码片段本地 git 检出只给坐标不给内容（私有仓库不进交付包）

这样你要的闭环就成立了：口之上的一切——路径、节点弹窗、阅读器、答题、结算、图鉴、复习—— 是一份代码。你每天用 local 时发现的任何问题，改在口之上，online 自动就有了。 口之下只有四个小适配器，各几十行。
而 local 保持离线，这不是妥协，这是保护你每天要用的那一端。

Grok 和 Gemini 独立审计后给了同一句结论。Grok 原话： 「不要让 local 去用 SwimmerBackend——那是在拆掉你每天用的那一端， 而且对『local 发现的问题自动惠及 online』几乎没有帮助。」

顺带查出一个两份 spec 自己打架的地方（需要你裁决）

SPEC-0001:141：共享包不得拥有「任何 3D、世界地图、关卡或激励系统」。
SPEC-0003:122：「把场景搬进 packages/ui」——而 packages/ui 就是共享包。

两个模型独立给出同一个解法，我也认同：新建 packages/world。 这样 SPEC-0001「共享课文包不碰 3D」成立，SPEC-0003「一个场景两个覆盖层」也成立。 代价：apps/local 需要装 three 系列依赖（它现在没有）——但只有 local 选择依赖 packages/world 时才装，packages/ui 保持零 three。

按 CLAUDE.md 的 Upstream Rule，改 spec 不是我能自己决定的。 这条要么你拍板改 SPEC-0003 的第 1 步，要么在 PGS 上游提。
