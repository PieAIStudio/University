# 支付：浏览器已接好，钱进来还缺后端

这是一份跨仓库缺口说明。它记录 University 这边已经交付的浏览器契约，
以及真正收钱、验回调、给钱包加额度还必须在 SwimmerBackend 完成的工作。
这里的“建议”是给项目负责人的判断材料，不是替后端仓库拍板。

## 先给结论

支付不是第四个 mode 边界。

现有 `apps/university/src/ports/` 的三类差异回答的是：AI 从哪里来、课文
材料从哪里来、能不能触达课文背后的源码仓库。支付不回答其中任何一个问题；
作者端和投放端都应该绑定同一个账号、读同一个钱包和权益、请求同一种订单。
所以没有新增 `apps/university/src/ports/payment.ts`，也没有改
`AGENTS.md` 或 V5 的边界法律。

支付契约放在共享 core，浏览器的 SwimmerBackend 适配放在共享 backend 包：

| 位置 | 现在负责什么 |
| --- | --- |
| `packages/core/src/ports/payment.ts` | 定义账号、余额、权益、订单和不可用能力的共享契约；保留订单 id 幂等请求 |
| `packages/backend/src/payment.ts` | 只把已有的 `wallet_get_balance` 映射给浏览器，并用浏览器的 `crypto.randomUUID()` 生成订单 id |
| `apps/university/src/account/identity.ts` | 从同一个 backend assembly 导出支付能力；不创建第二个客户端 |
| `packages/ui/src/navigation/screens/PlansScreen.tsx` | 展示余额和权益，保留购买位置，展示订单状态；成功后重新读权益 |

这条线到这里的状态是：**浏览器可以请求一个渠道无关的购买能力，但当前
没有可供它调用的 University 订单服务，所以不会假装付款已经可用。**

## University 这边已经做了什么

### 读，不改钱包

`PaymentPort` 提供五个浏览器动作：

- 读服务端钱包余额；
- 读当前账号权益；
- 用一个产品自己的 `offerId` 发起购买请求；
- 用同一个订单号查询订单状态；
- 购买成功后重新读取权益。

浏览器只调用 `wallet_get_balance`。`wallet_grant`、`wallet_reserve`、
`wallet_commit` 和 `wallet_refund` 没有暴露给浏览器购买流程。尤其是，
页面不会因为用户点了按钮就自行增加额度，也不会把“收到一个前端成功响应”
当成付款成功。

### 订单号由浏览器生成，但浏览器不是最终幂等闸

没有传入订单号时，浏览器用 `crypto.randomUUID()` 生成一个 UUID。一次页面
会话内，重复使用同一个订单号和同一个 `offerId` 会复用同一个请求，不会再
发第二次创建请求；换一个 `offerId` 复用同一个订单号会被拒绝。

这只是减少双击和同页重试的第一道闸。刷新页面、清空内存或伪造请求都会绕过
浏览器缓存，所以 SwimmerBackend 仍必须以数据库唯一约束和原子结算作为最终
幂等闸。测试证据在 `packages/core/src/ports/payment.test.ts`：同一 id 的两次
请求只调用一次 `createOrder`；`packages/backend/src/payment.test.ts` 则确认
浏览器适配只读 `wallet_get_balance`，没有调用任何钱包变更 RPC。

### 没有渠道时，入口仍然存在

会员页仍显示“付费权益”“待产品确认”和“查看购买入口”。待产品确认是
占位，不是价格，也不是已经存在的付费档位；页面没有编造金额或周期。

点击后，如果账号已登录但服务端还没有 University 订单入口，会打开共享的
能力说明：

> 购买入口还没接好
>
> 接通后，这里会为你的账号生成一个订单号，并把你交给服务端选择可用的支付渠道；
> 付款成功后，服务端才会更新钱包和权益。
>
> 当前还没有发布给 University 使用的服务端订单入口。浏览器不会直连支付
> SDK，也不会自己给钱包加额度。
>
> 待产品确认价格后，服务端会统一接入国内和海外渠道，验证付款回调，按订单
> 幂等结算，再让这里刷新权益。

未登录时会先说明“请先登录再购买”，因为钱包和订单必须绑定账号；这不是把
购买按钮藏掉，也不是把按钮永久禁用。无论作者端还是投放端，学习内容仍按
现有公开课程和免费基线工作。

## SwimmerBackend 还缺什么

下面是“钱进来”真正落地所需的后端能力。它们不应在 University 仓库里用
前端代码、浏览器表或 Supabase 函数副本补出来。

### 1. 一份能覆盖两个渠道的订单表

后端需要一份权威订单记录，至少能把下面几件事连起来：账号、University
的产品/权益标识、浏览器订单号、选择的渠道、金额和货币、test/live 模式、
渠道方订单号、当前状态、创建/更新时间，以及退款或取消所需的状态信息。

金额和可购买的权益必须由服务端认可的产品配置决定；浏览器传来的金额不能
成为收费依据。订单号需要有数据库级唯一约束，至少按应用和账号隔离，重复
的创建请求要返回原订单，而不是再开一笔收费流程。

还需要一个面向浏览器的“创建订单”和“查订单状态”接口。创建接口只负责
建立或返回订单、选择服务端允许的渠道并返回下一步信息；它不接受浏览器
声称的“已付款”。查询接口也只返回后端已验证的状态。

### 2. 一份 webhook 事件幂等表

微信、支付宝和海外服务商都会重复发送回调，也可能延迟或乱序。后端需要
按“服务商 + test/live 模式 + 服务商事件 id”去重的事件表，记录验签结果、
接收时间、处理状态、关联订单和必要的错误信息。

收到回调时，服务端必须先验证签名、环境和金额，再把事件记下来；同一事件
再次到达只能返回已处理或继续安全重试，不能再次给钱包加额度。原始回调
数据如果要保存，也应放在后端受控位置，不能把密钥或验签责任交给浏览器。

### 3. 成功后的原子结算和 `wallet_grant`

验证通过的付款回调需要进入一条原子结算路径：

1. 锁定订单，确认它属于正确的账号、产品、金额和环境；
2. 如果订单已经结算，直接返回幂等成功；
3. 将订单标成已支付，并按订单 id 生成唯一的结算幂等键；
4. 调用 `wallet_grant` 给该账号发放服务端确认的额度；
5. 更新可读的权益/授予记录，让后续查询能读到新权益；
6. 订单、事件、钱包发放和权益更新要能一起提交，或由后端已有的原子结算
   机制保证不会出现“订单已支付但额度没发、重试又发两次”的中间状态。

失败、取消、退款也需要明确状态迁移和补偿路径。`wallet_reserve`、
`wallet_commit`、`wallet_refund` 是钱包已有的另一组能力，不能被浏览器拿来
模拟“收款成功”；本轮 University 只读余额并请求订单。

### 4. 两个渠道适配器，但一个结算内核

用户已经决定国内和海外都要。后端可以分别接入国内渠道（例如微信支付、
支付宝）和海外服务商（例如 Stripe，具体服务商待定），但渠道差异应停留在
后端适配器：创建付款、验签、把回调翻译成统一事件。

统一订单状态、webhook 去重、原子结算、退款和 `wallet_grant` 的内核不应按
渠道各复制一份。University 浏览器只看到统一的 `offerId`、订单状态和
可选的 checkout URL，不知道也不需要知道当前用的是哪家服务商。

## `paid_credit_purchases`：提升共享，还是复制？

### 推荐：把 Collapse 机器提升成可复用的平台能力

推荐在 SwimmerBackend 把 Collapse 现有的
`collapse.paid_credit_purchases`、`collapse.paid_credit_provider_events`
和原子结算函数，整理成**平台级、带应用/产品命名空间的付费额度购买能力**，
再让 Collapse 和 University 都复用它。可以先做一个兼容层或版本化迁移，
保住 Collapse 现在的行为，再把 University 接到同一套内核；这不是要求把
University 的产品字段硬塞进 Collapse，而是把已验证的收钱不变量提到拥有
钱包的仓库。

理由很直接：支付回调、验签、重复事件、退款和“只发一次额度”都是钱的安全
边界，不是某个学习产品的页面细节。共享后，`wallet_grant` 的唯一来源、
审计路径和修复点只有一处，也不会再出现 `sea.orders` 加上 Collapse 表，
最后 University 又有第三份不一样订单表的局面。这符合项目“共享代码”和
“kit 做不到就改 kit，不在产品里 fork”的法律。

这只是建议，不是本仓库已经完成的后端变更。后端负责人仍需确认平台表的
命名空间、权限、RLS、应用配置、价格快照、退款语义、迁移顺序和兼容旧
Collapse 订单。

### 提升共享的代价

- 需要先抽象出真正跨产品的字段和状态，不能把 Collapse 的命名和特殊权益
  假装成通用模型。
- 需要迁移现有 Collapse 数据或提供兼容视图/适配器；迁移期间要同时验证
  旧订单查询、退款和重放 webhook。
- 共享内核的发布、权限和回滚影响多个产品，审查和测试范围会比 University
  单独接一张表更大。
- University 的 `offerId`、权益授予和国内渠道规则仍要有自己的配置，抽象
  不等于产品需求自动消失。

### University 复制一份的短期收益与长期代价

复制看起来更快：University 可以自定字段、自己排期，不必等待 Collapse
迁移，也能先做一个只服务本产品的订单查询。

但这会让两套代码分别处理相同的高风险问题：webhook 重复、金额校验、test/live
隔离、退款、失败重试、钱包发放和审计。之后还会有两套订单状态、一套
`collapse.paid_credit_purchases`、一套 University 表，外加已有的 `sea.orders`。
修一个“重复回调发两次额度”的漏洞时，必须判断另外两套是否也有同样问题；
产品越多，漂移和运营对账越贵。除非平台负责人明确拒绝共享并接受这项长期
维护成本，否则不推荐复制。

## 用户在接入前要准备什么

下面是非技术的前置条件。具体要求会随国家/地区、公司所在地和服务商变化，
请让财务或法律顾问按实际业务确认；它们不是代码可以替用户补齐的。

1. **一个能收款的企业主体。** 通常要有公司或个体工商户等被服务商接受的
   主体、负责人身份资料、收款银行账户，以及开票、退款和税务安排。个人
   账号能不能收款不能想当然，先看目标市场和服务商规则。
2. **国内商户资质。** 如果上线国内渠道，分别申请并审核微信支付、支付宝
   等服务商要求的商户号，准备营业执照、结算账户、经营范围、客服/退款
   信息等材料。商户号就是服务商用来识别“谁在收钱”的账号，不是 University
   里的用户 id。
3. **网站和备案/合规材料。** 国内上线常常还涉及域名、网站或应用备案、
   隐私政策、用户协议、价格说明、发票和退款规则；究竟需要哪一种备案，
   取决于部署形态和所选支付产品，要在申请前向服务商核实。
4. **海外收款账号。** 如果接 Stripe 或其他海外服务商，需要注册并通过
   企业与负责人验证，准备可收款的银行账户、业务描述、支持的国家/地区、
   货币和税务信息。Stripe 账号只是“让服务商知道谁在收钱”，不会自动替
   University 完成国内商户接入。
5. **测试和正式两套资料。** 国内外渠道都要分别确认 test/live 模式、回调
   地址、签名密钥、退款权限和对账下载。密钥只放 SwimmerBackend 的服务端
   秘密配置里，绝不放进 Vite 环境变量、页面源码或浏览器 localStorage。
6. **产品定价和权益表。** 目前价格、货币、周期、可买权益和退款政策都还
   没有定案。没有这张产品表，后端不能安全生成订单，页面也只能显示“待
   产品确认”；不能先填一个看起来合理的数字。

## 下一步的交接顺序

```text
产品确认 offer / 价格 / 退款规则
        ↓
SwimmerBackend 提升或包装共享购买内核
        ↓
订单表 + 创建/查询接口 + webhook 幂等表
        ↓
国内/海外渠道适配与验签（服务端）
        ↓
原子结算 → wallet_grant → 权益可读
        ↓
University PaymentTransport 补齐 createOrder / getOrderStatus / readEntitlement
        ↓
PlansScreen 在真实 test 环境完成浏览器验收
```

在后端接口和产品配置完成前，University 这边的安全状态就是当前状态：余额
可读时读余额，购买入口保持可见但诚实说明未接通，不接任何支付 SDK，也不
自行发放额度。
