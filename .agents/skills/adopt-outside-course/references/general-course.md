# 通用课，和它为什么必须一眼看得出来

## 两类课

| | 实战学习 | 通用课 |
| --- | --- | --- |
| 例子 | TuringPact · Buzz · SupaLuv · UniversityLocal | 前端基础 · 产品方法 · 工具用法 |
| 背后有可运行的仓库 | 有 | 没有 |
| 出处 | commit + 文件 + 行号，指向真实代码 | MDN / RFC / 官方文档 |
| 「跑一下这个版本」 | 有 | 没有 |
| 地位 | **主打** | 并列陈列，标记清楚 |

## 为什么必须标记，而且是三处

产品的承诺是「每一段解释旁边都是真实存在的代码」。这句承诺不是分课生效的，
它是**整个产品的**。

> **只要有一个人点开一节课、期待代码证据、发现没有，
> 这条承诺对全部课同时失效。**

他不会想「哦这节是通用课」。他会想「原来那个卖点是吹的」。

所以标记要出现在**三个地方**：课程卡上、进关卡片上、课文页顶上。
只标一处，人就会在另外两处被骗到。

## 打个比方

菜单上写「本店牛肉全部可查溯源」。后来加了几道素菜，素菜没有溯源——这很正常。

但如果素菜和牛肉**印在同一栏、长得一模一样**，客人点了素菜去查溯源查不到，
他不会想「哦这是素菜」，他会想**「这家店的溯源是假的」**。

一道菜的问题，砸的是整本菜单。

## 通用课不是二等公民

标记它，不是因为它次一等。

通用课解决的是实战课解决不了的问题：**一个人在能读懂真实仓库之前，
需要先知道「前端」「组件」「状态」是什么。**没有这一层，实战课的门槛就把人挡在外面。

标记只说明**它的可信度建立在什么之上**——一个引 MDN，一个引 commit。
两种都是真的，只是不同的真。

## 出处：绝不引用被参考的那门课

通用课的引用**只能指向权威原始资料**：MDN、RFC、W3C、官方文档、规范。

**绝不引用我们参考的那门课，一次都不行。**

两个理由，第二个更重要：

1. **说好的。** 这是和原作者沟通过的边界。
2. **它其实让课更好。** 一个说法找不到权威出处，通常不是因为没人写过，
   而是因为它是某个人的经验或习惯。经验可以讲，但要讲成「很多人这么做」，
   不能讲成「事实就是这样」。
   **这条规矩顺带挡住了课文里最常见的一类错误。**

## 一门通用课的来历，只有一种正确写法

课文是我们自己写的。引用的是 MDN 和官方文档。**这就是它的全部来历。**

外部课程在这个流程里的角色是**目录**——它告诉我们讲什么、按什么顺序讲。
目录不是原文，提纲不是素材。
