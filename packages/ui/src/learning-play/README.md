# 互动课件

## 互动主线实验（`interaction-path`）

除原有十三种独立玩法外，共享阅读器支持一个显式选择加入的连续回合载荷。
它不是第十四个大型模拟器，也不是第二套课程格式：仍然通过现有课程 CLI、
`LessonActivitySchema` 和 recovery 包写入。一节实验课只放一个 path，内部由
`decision`（先判断再反馈）、`evidence`（点出材料依据）、`assemble`（组装或修补
可用文本）组成三至八轮。首轮为判断，至少有一次材料定位和一次组装；组装之后
可以再换条件判断，不强迫最后一轮的控件形状。

宿主在 `learning-play.css` 后导入包导出的 `learning-play/interaction-path.css`；
两种 app 模式已在同一入口导入，不通过组件内部或隐藏的 CSS 导入链加载。

不得为凑轮数在作品后再问同义选择题。本轮三节样课各用四轮，以作品收口。
`evidence.task: "unsupported"` 必须提供 `material.reference: { label, text }`，
把短来源记录放在明确标为教学草稿的待选句旁；不是凭空猜哪个句子假。
`support` 仍是从忠实简述的材料里定位支持句。`initialPieceIds` 可以装入待修
草稿，用户保留正确部分并移除错误；已装入的片段不在备选区重复显示。
选入、移除与移动之后，键盘焦点回到对应实际对象；提交之后反馈与下一步
一起滚入可见范围，不把继续按钮留在屏外。图片首轮显示，后续按需重看。

每轮有明确任务、可选提示和提交后的解释。来源使用课节 evidence 中已有的引用，
图片只引用课节已有的 `assetId`。材料选项必须是忠实摘译或明确标记的教学草稿，
不能把虚构的干扰项标成来源原文。组装约束按片段 ID 确定性检查：保留、排除、
选一项及必要的先后关系；非必要顺序全部接受，不用自由文本关键词猜测评分。

原文保留为按需展开的复习内容，正文仅保留一个 `::play{#id}`，阅读器将它提升为
主线后不在原文中重复渲染。完整原文的阅读工具随原文展开。顶部显示互动轮数，
不是未展开的文章章节。引导完成只形成当前访问内的操作记录和可复制产物；首答、
改答、提示、看过讲解和重开分别记录。切换账号、课节、版本或语言不串答案。
这不是长期学习统计或独立掌握证据，离开页面后不承诺保存回合现场。

原有独立练习、明确学习确认及云进度实现不变；跳去练习是导航，不是互动完成。
两种模式共享渲染器，没有新的模型调用或按课程 ID 硬编码。所有显示文案均提供
英语字典，图片保留替代文字和可展开的来源说明。点击、键盘移除与排序不依赖拖拽。

载荷和纯规则：`packages/core/src/learning-play/interaction-path.ts`；通用可运行
示例：`packages/core/fixtures/interaction-path.json`；实验状态与样课验收见
[互动主线实验](../../../../docs/plans/active/interaction-first-experiment.md)。

面向学习者与课程编写统一称“互动课件”。它是跨领域共享的教学方式，不是AI与游戏星球的专属课程。
代码里的既有 `learning-play` 路径、组件类型与活动ID保持不变；课程工作线按下方契约逐课选用，不在目录基线阶段批量嵌入。

`/play-lab/ai` 是“用 AI 做产品”合集；`/play-lab` 保留“编程原理”合集。两种模式共用同一页面和组件；两个合集分别装哪几种玩法，以 `LearningPlayLab.tsx` 的 `FOUNDATION_MODES` / `AI_MODES` 为准——这里原本手写了一个数字，`contrast` 和 `weigh` 落地时它没跟着改。可单独试玩，也可顺序连玩一个合集；练习页仍有入口。

## 嵌入一个活动

```tsx
import type { LearningActivitySpec, ActivityResult } from "@pieai/university-core";
import { LearningActivity } from "@pieai/university-ui/learning-play/LearningActivity.js";

function ActivitySection({ activity }: { activity: LearningActivitySpec }) {
  function recordEvidence(result: ActivityResult) {
    // 交给调用者的既有练习流程。completed 和 skipped 必须分开处理。
    // 不凭一次通关直接声明掌握，不在组件里发 XP 或写课程完成状态。
    console.info(result);
  }
  return <LearningActivity activity={activity} onResult={recordEvidence} />;
}
```

应用入口已经统一导入 `learning-play.css`、`sort.css`、`contrast.css`、`weigh.css`、`hunt.css`、`dispatch.css`、`program.css`、
`ai-play.css`、`ai-workflow.css`、`ai-quality.css`、`ai-context-play.css`、`ai-agent-play.css`、`play-usability.css`、`workflow-usability.css`、`quality-usability.css`。其他宿主需从相同包的 `learning-play/`
导出路径导入所使用合集的样式，并使用既有 I18n/品牌主题上下文。基础外壳始终需要
`learning-play.css`；AI 组需要上述五份 `ai-*` 样式；新的默认引导还需三份 `*-usability.css`，按应用入口的顺序导入。
可选 `onNext` 与 `nextLabel` 由宿主决定下一步，组件不认识课程或播放列表。

活动以 `id` 标识；切换 `id` 或点重新开始会创建新一轮。每轮只发一个结果：完成或跳过。
同一 `id` 表示同一活动定义；修改内容时应使用新的修订 `id`。连续试玩重新进入同一活动时，宿主也可以设置新的 React `key`。
停止执行保留指令，重新开始清空整轮；卸载、切换或跳过会取消尚未结束的播放。

## 难度与上手提示分别配置

**先分清两件事，它们长得像但不是一回事：**

- **试玩页的情境**有 `intro`（入门）/ `practice`（进阶）/ `challenge`（挑战）三份明确载荷，读者可以随时换档。这是 `ActivityFamily`，由 `packages/ui/src/learning-play/*-difficulty.ts` 从一份素材展开出来——那六个文件是**试玩页的示例数据**，不是课文功能。
- **课文里的组件只存一份载荷**，外加一个 `difficulty` 标签（`LessonActivitySchema`）。它没有 family，读者也换不了档；那个标签只用来告诉读者这一关的分量，并记进完成证据。

所以下面这段是**试玩页**的用法。课文配组件不需要写三份，写一份、标好 `difficulty` 就够了。要不要让课文里也能换档，见 [ADR-0010](../../../../docs/adr/ADR-0010-difficulty-moves-when-the-learner-moves-it.md) 的「什么还开着」。

每个情境三份难度配置，而规则实现仍然只有每种玩法一套。

课文里的三档走另一条路：同一个 `family`、同一个 `kind`、不同 `difficulty` 的几个
activity 由 `groupActivityLevels` 归成一组，`LearningActivity` 在头部渲染切档按钮。
`ActivityFamily` 要求三档齐全（play lab 自己的例子能保证），课文那条是部分 map ——
一节课写一档也合法，而且现有二十七节都是一档。`ActivityFamily` 的三份载荷必须同 kind、各有唯一 id、并标明对应 difficulty；`selectActivityLevel` 检查这些身份约束，不对分数、目标或计时做通用乘法。

```tsx
import { selectActivityLevel, type ActivityFamily } from "@pieai/university-core";

// 试玩页的用法：一份 family，读者在三档之间切换。课文不是这样调的。
function PlayLabActivity({ family }: { family: ActivityFamily }) {
  const activity = selectActivityLevel(family, "intro");
  return (
    <LearningActivity
      occurrenceId="lesson-context-1-practice-1"
      activity={activity}
      initialGuidance="guided"
      onResult={(result) => console.info(result)}
    />
  );
}
```

`occurrenceId` 标识一次课节里的位置；同一素材在另一节出现要换 occurrenceId。换活动 id、难度或 occurrenceId 会重新开始并取消旧播放。切换界面的“自由探索 / 跟着提示玩”只改变呈现，保留工作和收据。结果带 `difficulty`、`occurrenceId`、`guidanceUsed`，因此入门完成或用了帮助都不会冒充挑战/独立完成。尚未声明 difficulty 的既有直接载荷按 practice 记账，以兼容旧调用。

试玩页默认入门；每个组件可以即时换档。难度不是账号等级、课程系列编号，也不会自动决定下一题。连玩允许不同关选不同难度；完成标记保留到本次会话，不写 XP 或课程进度。

### AI 配课的选择顺序

1. 先说清本节要练的一个判断，如“核对资料来源”，再选组件 kind。
2. 列出学习者已经会做的动作和题目已给的事实。第一次接触、复习或长课中的轻任务用 intro；已会基本操作、需要组合判断用 practice；需要迁移、交叉条件或保住旧行为时才用 challenge。
3. 从同一 family 明确选择一档。后期课程可以穿插 intro；每一节不必放组件，每一节也不必全选同档。不要因“第十系列”批量标成挑战。
4. 检查本档 goal、关键约束和真实完成证据是否匹配课程内容。帮助的开关不改变完成规则，不作为升难办法；计时不是三档难度的定义。
5. 为课节位置设置独立 occurrenceId，调用既有课程生产/校验流程。`difficulty-examples.ts` 只扩展试玩页的预设案例。**课文配组件写一份载荷、标好 `difficulty` 即可——`LessonActivitySchema` 里没有 family 这个字段**（这里原来写的是「自定义活动要写显式 family」，照做是做不成的）。任何情况下都不能把任意 JSON 交给这个 fixture factory 或绕过课程 CLI。

| 玩法  | 入门                  | 进阶                       | 挑战的真实新增判断                                         |
| ----- | --------------------- | -------------------------- | ---------------------------------------------------------- |
| 接线  | 三节点、两关系        | 全因果链与分支             | 失败后重新尝试的回路及探针                                 |
| 调参  | 另一变量固化为常量    | 两变量取舍                 | 图片最低宽度等独立约束；工作队列更紧的产出/等待/内存可行域 |
| 反例  | 分界附近的小范围      | 完整输入范围               | 小于、等于、大于故障分界都留实际测试记录                   |
| 调度  | 三请求认识服务/复用   | 七请求混合处理             | 同名新版缓存键与必须实时查询交错                           |
| 指令  | 先到近处目标          | 原路径与检查点             | 新检查点使原解失效，需要绕行                               |
| 原型  | 两项给定，只问一项    | 自己写三项约定             | 初次验收后的客户变更与再次验收                             |
| 装箱  | 一顾客、两份来源      | 多顾客与来源冲突           | 8格约束要求摘取，仍允许充分的不同组合                      |
| 对照  | 一致与分开各一个情况  | 加上聪明那种反而输的情况   | 两边落在同一处、而那一处并不是要找的那个                   |
| 取舍  | 两种情况，答案换边    | 四种情况，每个选项各赢两次 | 多一个"先问一句"，再判它什么时候也不管用                   |
| Agent | 读取并写一份草稿      | 混合写入与材料指令         | 后续动作出现第二种保护文件，旧进阶行动记录不够             |
| 评测  | 正例+一种边界         | 四类请求                   | 缺信息+无资源、缺信息+越界也要独立成题并回归               |
| 返工  | 两改法、原问题+旧功能 | 三改法与双版检查           | 保留A把B改C，或改选后两次重开都正确                        |

入门给定的是事实/配置，不是伪造的操作：Brief 的 `providedChoices` 和 `learnerChoices` 分开；Eval 入门题按下试跑才生成真实回执。挑战的扩展同样由原引擎验收：Hunt 聚合并重算三侧记录，Eval 检查交叉条件覆盖，Repair 检查业务保留项及实际重开时点。每档都有可运行的维护用解，但这些解不发给学习者当按钮。 新增 family 还须提交三档的任务差异、可运行解和至少一条更低档证据不足的反例；类型检查只证明载荷形状与身份，不自动证明主观难度。

## 选择哪种玩法

| 类型         | 适合的学习目标                                     | 载荷定义                                                     | 通关证据                                             |
| ------------ | -------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------- |
| `connect`    | 解释依赖关系、原因与结果、成功/失败分支            | 节点、必需关系及说明、探针路径                               | 用户实际建立的关系与执行过的路径                     |
| `sort`       | 划界与归类：这算不算 X、它属于哪一层               | 格子、每样东西的归属和理由、可选的诱饵格与它不成立的原因     | 每样东西的落点、放错次数与看过的反驳                 |
| `contrast`   | 对照两种做法：看起来一样，其实在什么情况下会分开   | 两种做法、若干情况、每种做法在每个情况下的结果               | 每个情况的预测对错、两边实际落点                     |
| `weigh`      | 一笔取舍：这个选择买到什么、代价是什么、何时反过来 | 两到多个选项、若干情况、每个情况的正解与另一选择在此处的代价 | 每个情况的选择、选错次数、哪个选项赢了哪些情况       |
| `tune`       | 理解多变量取舍、寻找可行解                         | 控制范围、算术表达式、同时成立的目标、模型说明               | 参数、所有指标、近期实验对照                         |
| `hunt`       | 边界测试、反驳一个声称成立的规则                   | `threshold` 或 `clamp` 模型、规格、输入范围                  | 实际输入、期望/实际输出、探索记录                    |
| `dispatch`   | 资源复用、状态变化、预算下的决策                   | 请求序列、处理通道、成本、缓存键                             | 处理顺序、累计成本、复用情况与错误尝试               |
| `program`    | 顺序、方向、循环、约束同时成立                     | 网格、障碍、检查点、起终点、指令上限                         | 指令、每步执行轨迹、最终状态                         |
| `ai-brief`   | 将模糊想法变成能验收的产品行为                     | 访谈、行为轴、两种预设解释和目标约定                         | 初次约定及客户变更后，当前规则下实际试用的两轮证据   |
| `ai-context` | 为 AI 选取充分、适用、有来源的材料                 | 来源文件、段落、事实、授权依据和示意容量                     | 材料包、来源、冲突/缺口、当前生成版本的顾客试用记录  |
| `ai-agent`   | 区分工具能力、任务授权和材料内的指令               | 能力类型、文件、范围、动作和目标产物                         | 实际文件、权限、执行/拒绝/恢复记录及保留项           |
| `ai-eval`    | 先定要求和测试，再检验 AI 产品边界                 | 条件轴、产品约定、预设响应和产品检查                         | 冻结用例、逐次响应、保留的失败收藏、带边界整组复跑   |
| `ai-repair`  | 用可复现证据要求 AI 小步修改                       | 可操作产品、故障、预设修改和旧功能要求                       | 原始失败、双版同路径对照、时间分支、手工回归及检查点 |

规则实现位于 `packages/core/src/learning-play/`，全部确定性运行，不调用模型或执行载荷内的代码。
`tune` 的表达式支持有限深度的加法、乘法、最小值与最大值；可选图片细节/工作队列示意绑定同一组指标或参数。
图片模糊与队列均为教学示意，不是实际图片编码器或性能测试。
`hunt` 目前只提供两种明确的数值模型；新模型应扩展核心规则和测试，不能用字符串 `eval`。
这些是本地类型化组件载荷，尚不是可从任意来源导入的课程 JSON 协议；将其纳入课节必须通过现有课程 CLI、校验和发布合同。

## 覆盖不到的形状：上一轮缺的两种，这一轮补上了（2026-09-10 实测）

把 browser-ai 的十五节已发布课逐节送进 [选组件规则](../../../../apps/local/.agents/skills/write-lesson/references/activities.md)
判一遍，**五节配上，十节没配**。五节全是 `connect`，而且是四种不同的图——交叉配对、
五节点直链、分叉、两条平行输入汇聚——所以 `connect` 是真通用，不是同一个游戏换皮。

那十节不配的**为什么**，逐条读下来，绝大多数不是"这节课不该有互动"，
而是**它要的手部动作，当时的十种里没有**：

| 课文在做的事               | 当时撞上的问题                                  | 现在                     |
| -------------------------- | ----------------------------------------------- | ------------------------ |
| **划界**：这算不算 X       | 没有"归类"形状                                  | `sort`（2026-09-10）     |
| **归类**：这一个属于哪一层 | 同上                                            | `sort`                   |
| **对照两种做法**           | 只有恰好是图的对比能用 `connect`                | `contrast`（2026-09-10） |
| **一笔取舍**               | 没有"权衡"形状；`dispatch` 是预算调度，不是取舍 | `weigh`（2026-09-10）    |

缺口是按整个书架的形状分布补的，不是按手感补的。469 节课按变体分：
**现象 140、对比 117、决策 104、溯源 48、术语 41。**
对比加决策是 221 节，**接近一半的书架**，而这两种当时都没有落脚点——
所以先补的是 `contrast` 和 `weigh`。

### 补完之后实测了一次

从八门不同的课里各取若干节**当时没有组件**的真课文，共十六节（对比八、决策八），
连同两个新引擎的源码一起交给一个模型，要求它判断配不配得上、配得上就写出完整载荷，
**并且每个载荷都由真引擎 `isValidContrastActivity` / `isValidWeighActivity` 复验**：

- **contrast 5 节、weigh 5 节**——这十节在两个新玩法出现之前都无处可去；
- **另外 6 节判给了已有玩法**（`sort` 2、`connect` 3、`hunt` 1）；
- **判"不配"的：0 节**；
- **十个载荷全部通过真引擎**（10/10），不是通过一份手抄的规格。

这不能证明这十节的载荷好玩，也不能证明真人读了会更懂——那需要真实试学。
它能证明的是一件具体的事：**"每节课都要有互动"从此不是一句会逼出硬凑的口号**，
十六节真课文里没有一节是被迫的。

两种情况**不算缺口**，为了不把数字读大，单独列出来：一节因为删除测试没过（开场和中段
已经把话说完，再配只是重画一遍），一节是 `tune` 在主题上对得上、但课文里没有真数可填，
那是材料不足不是形状不足。

### 然后把一整门课真的配满了（2026-09-10）

上面那次是纸面实测：判断配不配、写出载荷、过引擎。之后 browser-ai 这门课
**四门课程二十七节全部写完并配上组件**，这是第一份不是抽样的数字：

- **27 / 27 节有组件**，每节一个，没有一节是零；
- 用到 **十三种里的十种**：`sort` 7、`connect` 6、`contrast` 5、`weigh` 3，
  `tune` / `dispatch` / `ai-context` / `ai-agent` / `ai-eval` / `ai-repair` 各 1；
- **没用到的三种**：`hunt`、`program`、`ai-brief`。

那三种没用上，各有各的原因，写下来是因为它们不一样：`program` 要一张网格和一条
能走的路线，这门课没有一节在讲路线；`ai-brief` 刚解开，这一轮的课文没有一节的教法是
「把含糊要求钉成能验收的行为」；`hunt` 则是**被撤下来的**——它一度配在一节讲定性判断的
课上，载荷里那个 0–10 的刻度是为了配组件现编的，课文里没有这个数。换成了 `sort`，
用课文自己的那条分界。**这一节是这一轮唯一一次硬凑，它是被读出来的，不是被闸门读出来的**：
载荷合法、引擎通关、闸门全绿。

所以「每节都要有互动」这条硬规矩，在一门真课上的代价是可测的：27 节里 1 节需要换形状，
0 节需要放弃。

**给下一个人的一句话**：现在判"配不上"之前，先把十三种都过一遍——
尤其是 `sort` / `contrast` / `weigh` 这三种只要求读者会读中文的。
真的十三种都不行，那句理由要写进 agent report，它比一个硬凑的载荷有用得多；
上面这三种玩法就是上一轮的"配不上"理由攒出来的。

## 哪些玩法真的能装进任何一门课（2026-09-10）

问「组件是不是硬绑定」，答案不是一句话，是三档：

**空框，任何课都能装（9 种 = 编程原理那 8 种，加上刚解开的 `ai-brief`）：**
`connect`、`sort`、`contrast`、`weigh`、`tune`、`hunt`、`dispatch`、`program`、
`ai-brief`——载荷决定读者看到的每一个字。

**`ai-brief` 是这一轮解开的那一个。** 它原来把三条约定轴写死在引擎里
（`access` / `confirmation` / `roster`），值也是写死的字面量，所以任何一门课想用
「把含糊的要求钉成能验收的行为」这个教法，读者看到的都是同一个报名产品。
现在轴来自这节课自己的提问、动作和结果来自载荷，引擎里不再有任何一个产品名词——
[引擎测试](../../../core/src/learning-play/ai-brief.test.ts)整份是一个「分享文件」
的产品，一个报名相关的词都没有，这是唯一能证明词是真的没了、而不是改了名的办法。

### 上面那句「仍然绑定 4 种」是错的，这里是量过之后的版本（2026-09-11）

原文写的是 `ai-context`、`ai-agent`、`ai-eval`、`ai-repair`
「情境、界面文案和状态机仍然写死在共享 i18n 和渲染器里」。**关于 i18n 和渲染器的
那半句不成立。** 把全部 zh-CN catalog 按「键 → 值」切开、逐个值查虚构产品名词
（咖啡店 / 会员卡 / 报名 / 门店），结果是：

- 含产品名词的键一共 **8 个**；
- 被**任何渲染器**引用的：**0 个**——它们全部只出现在试玩页的示例数据里
  （`ai-brief-examples.ts` 的 `walk`/`club`、`ai-workflow-examples.ts` 的
  `cafe`/`workshop`/`event`/`recipe`），而示例本来就该是具体场景。

所以十三个渲染器没有一个写死了某个虚构产品。**真正还绑着的是三处引擎层的形状约束，
而且它们约束的是"你能教什么形状的东西"，不是"读者会看到谁家的产品"：**

| 玩法        | 写死在引擎里的                         | 它实际限制了什么                             |
| ----------- | -------------------------------------- | -------------------------------------------- |
| `hunt`      | `model: "threshold" \| "clamp"`        | 只有这两种数值模型；定性的分界配不上         |
| `ai-repair` | `model: "booking" \| "preference"`     | 演示产品只有这两台状态机                     |
| `ai-eval`   | `EvalScenario` 的三条布尔轴 + 五种结果 | 轴数和结果类别固定，但每一条的说法都由载荷给 |

这个区别要紧，因为它改变下一个人该做什么：照原文去「把产品名词搬进载荷」，
会发现渲染器里根本没有产品名词可搬。要解的话，该解的是上表第二列——
而 `ai-eval` 那三条轴（信息够不够 / 东西在不在 / 在不在范围内）**可能根本不该解**，
它就是这个玩法要教的模型本身。

**这一条记在这里，是因为原来那句话是我自己写的，而它会把人派到一个空房间里。**

### 代价和用量是反着的（2026-09-11 实测）

把每种玩法的渲染器行数（含它自己的子组件）、引擎行数，和它在全部 469 节课里
被用到的次数放在一起，相关性几乎是负的：

| 玩法         | 渲染器 | 引擎 | 真课用过 |
| ------------ | -----: | ---: | -------: |
| `ai-agent`   |   1176 |  378 |        1 |
| `ai-repair`  |    943 |  616 |        1 |
| `ai-context` |    803 |  221 |        1 |
| `program`    |    797 |  209 |    **0** |
| `ai-eval`    |    762 |  355 |        1 |
| `ai-brief`   |    602 |  307 |    **0** |
| `dispatch`   |    470 |   96 |        1 |
| `hunt`       |    313 |   63 |    **0** |
| `connect`    |    298 |   36 |        6 |
| `tune`       |    284 |   50 |        1 |
| `weigh`      |    183 |  176 |        3 |
| `contrast`   |    171 |  165 |        5 |
| `sort`       |    143 |  131 |        7 |

**最便宜的四种（`sort`、`contrast`、`weigh`、`connect`，合计 795 行）扛了 27 个组件里的 21 个。
最贵的四种合计 3684 行，扛了 4 个。三种一次都没被用过，合计 1712 行。**

原因在表里看得见，不用猜：便宜的四种只要求读者会读中文，任何一节课都能给出
它们要的材料；贵的四种每一个都要求这节课**恰好**在讲一台有状态的机器——
文件和权限、可复现的故障、容量和来源、三条是/否条件。那不是缺陷，那是这些玩法
本来的教学内容；但它意味着**"十三种"对写课的 AI 来说其实是"十种加三种备用"**，
而把它们排成一张等长的十三行表，会让人以为选择是均匀的。

`activities.md` 的选型表因此加了第四列「这节课必须真有」，直接抄自各引擎的
`isValid*`。**判"配不上"之前先读那一列**：第三列说的是读者的手感，
决定配不配得上的是第四列。

**还没有做的决定**：那三种零使用的玩法（`program` / `ai-brief` / `hunt`，1712 行）
是留着等合适的课，还是退役。这个决定该由"接下来要写哪些课"来定，不该由行数来定，
所以这里只记录数字，不下结论。

## 组合与节奏

每个活动可以独立成为一段。也可以先接线解释关系，再调参数检验取舍，最后找反例检验边界；按学习目标选一到两个即可，不必凑齐五种。
调度默认不限时，熟悉后可开启 60 秒挑战；暂停、切到后台和超时都保留现场，超时后可以继续不限时练习。
音效继承共享设置；减少动效时保留同一执行结果与文字轨迹。

编程原理的示例在 `base-examples.ts`、`extra-examples.ts`、`program-examples.ts`；
AI 组在 `ai-brief-examples.ts`、`ai-workflow-examples.ts`、`ai-quality-examples.ts`。
只有试玩页面导入这些样例；内嵌组件不依赖试玩页面。

AI 组也可组成一段产品工作流：先用原型对焦澄清行为，再整理材料与工具范围，最后构造验收并带证据返工。
每种当前有独立的虚构情境；“连玩”只编排活动，不宣称五关已经连接成同一个真实项目。
正式配课时按学习目标选一至两种即可。这些需要思考和试验的任务默认没有计时惩罚。

## AI 教学沙盒的边界

AI 组明确标为预设案例。真实发生的是用户操作、沙盒数据变化与确定性验收；预设的是
候选产品假设、Agent 计划、候选响应和修改版本。没有模型网络调用、真实文件编辑、消息发送或发布，
也没有“提示词质量分”或伪造的模型成功率。将来接实际模型仍须经过既有端口与 SwimmerAIKit 的计量流程。

- Brief 可对两个预设产品执行同一个动作；不能只靠选中条款通关。可选 `followUp` 在首次验收后提出一次客户变更，保留其他已约定的规则，再收集当前规则下的新证据。首次验收是关内阶段，不提前发送完成结果。
- Context 的“格”只是教学容量；14、9、8 格都可能是充分材料，无额外节省奖励。`initialParagraphIds` 可提供待修材料包，`visitors` 让顾客直接试问生成页面。修改材料后必须重生成，并由当前版本重新接待顾客；只装好材料不算完成。
- Agent 工具能力和可达文件同时限制操作。任务来源不保证计划每一步都合适；导入文件的文字不增加授权。文件旁的开关与工具箱共用同一权限映射；自动推进遇材料指令、缺权限或将改动保留文件时停下，允许随时停止，后台也停止。检查点只恢复本地沙盒，保留审计与当前授权，不能类推为真实发送或支付均能撤销。
- Eval 先冻结输入与要求，每点一次只揭示一份预设响应。换候选或查看旧题保留该题证据；新增题保留已有发现，修改或删除只失效对应题的观察。更改用例或产品边界会要求整组复跑。多个方案可以被合理约束到完成任务，全部拒绝无法通过正常请求。
- Repair 的演示产品与重放使用同一个状态转换引擎。一套输入驱动旧版与候选版，可以逐步、拖动游标、跳到首次不同，再从该步接新操作。操作带保留最近四条探索分支，封存的原始失败独立保留。修掉原问题还须从空现场亲手检验旧功能；拖到操作带末尾、或带着回放前缀接操作，都不能冒充完整的手工回归。回退恢复版本与操作现场，并要求当前版本重新验收。

成功结果的 `submission.handoff` 是可复制的文本工作单；其他 `submission` 字段保留具体证据。
组件仅在完成时展示工作单，剪贴板不可用时仍允许直接选中文字。它来自虚构案例，使用前要替换为真实项目事实。
完成、跳过、尝试和线索仅是本轮操作证据，不写课程成绩、XP 或云端学习进度。

## 已知解与复核

这些是人工复核用的可行解，不是引擎唯一接受的答案。

- 接线：点击→请求→处理→响应→成功/失败；素材→剪辑→预览→检查→发布/修改。
- 调参图片：宽度 840、质量 80；也可宽度 1000、质量 65。任务批处理：每批 6、工作者 2；也可每批 4、工作者 3。
- 反例：包邮输入 100；音量输入 -1（任何范围内的负数都可以）。
- 网站调度：文件、实时、文件、缓存、实时、缓存、缓存。素材调度：素材库、制作服务、素材库、已有副本、制作服务、已有副本、已有副本。
- 邮差程序：前进×2、右转、前进×4、左转、前进×2。灌溉程序：前进×2、左转、前进×3、右转、前进×3、左转、前进。

维护的浏览器回归为 `e2e/learning-play.spec.ts`；规则/宿主测试与组件相邻。完整设计、研究依据、迭代记录与验收见 [已完成计划](../../../../docs/plans/completed/learning-play-lab.md)。
本轮能验证规则与交互成立。真人是否觉得好玩、能否举一反三与延迟记住，需要试学观察；不会从通关或点击数推断这些结论。

AI 组的人工复核路线（给维护者，学习界面不展示答案）：

- 原型：散步页选访客、审核、私有名单，然后真正提交并查看名单。客户变更后只把审核改成立即确认，再试。会员活动先登录、立即确认、公开昵称，客户变更后只改成私有名单并重试登录、报名和名单。
- 上下文：先点顾客，观察有冲突的现成页面；移出活动点子、装入签字价目表后重新生成，三位顾客重新试过再交付。第二情境可以用定稿、合同和问答各第一段组成 8 格材料包。
- Agent：给读取器必要文件；第二步只允许生成草稿，保留源表；材料要求的额外步骤可以退回，继续完成检查和预览。也可以故意扩大范围，看真实沙盒文件受损，再恢复检查点收窄范围。
- 评测：预约的方案甲遇缺日期题第一次追问、第二次却开单；商品的方案甲遇售罄题第三次才错误推荐。收藏四类条件，用对应的产品检查约束后整组重跑。方案乙加完整检查也可交付；全部拒绝不能通过正常请求。
- 返工：预约连点产生重复单后封存失败，版本 A 虽止住连点却破坏改约，版本 B 保留旧能力。偏好保存后重开才暴露失败，版本 B 锁死偏好，版本 A 才可改选。应用修改后逐步看双版，核对原问题，再亲手走旧功能。
